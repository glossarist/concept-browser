# URL Stability Policy

This document defines the URL stability contract that
`@glossarist/concept-browser` promises to its consumers and
downstream deployments. It is the source for the corresponding
clauses in the project README and in concept-model's
`ontologies/reference-docs/`.

The policy was formalized as part of the v0.8.x release stream
(see `TODO.streamline/14-backward-compatibility-and-urls.md`).

## Promises

### 1. Concept URIs remain resolvable forever

A concept URI minted in any Glossarist dataset remains resolvable
for the lifetime of the deployment. Specifically:

- If the concept is **withdrawn**, the URI still returns the
  historical record. The record carries
  `prov:invalidatedAtTime` and `gloss:hasStatus gloss:status/withdrawn`
  so consumers can detect the state without dereferencing heuristics.
- If the concept is **renamed** (slug change), the old URI returns
  a permanent redirect (see §2 below), not a 404.
- If the concept is **deleted** (a last-resort cleanup action), the
  URI returns 410 Gone with an explanatory page. This is reserved
  for legal/privacy removals and is documented per-dataset.

### 2. Concept URL paths are stable within a major version

The human-facing URL path is:

```
/dataset/{registerId}/concept/{conceptSlug}
```

- The slug is stable within a major dataset version. Renames within
  a major version emit a permanent redirect (see Redirects below).
- Major version changes (rare, coordinated) may re-sluginvalidate
  paths. Such changes are announced one minor version in advance
  and are accompanied by `migrations/` scripts in concept-model.

### 3. Resource URIs follow the same rule

All resource-bearing paths share the promise:

- `/dataset/{registerId}/concept/{id}`
- `/dataset/{registerId}/figure/{id}`
- `/dataset/{registerId}/stats`
- `/ontology/class/{classId}`, `/ontology/property/{propertyId}`,
  `/ontology/shape/{shapeId}`, `/ontology/taxonomy/{key}`
- `/resolve/{uri}` — universal deep-link

Renaming any of these (e.g., switching `/dataset/` to `/register/`)
is a major-version change.

### 4. Download URIs are stable within a major version

Per-concept downloadable RDF is served from:

```
/data/{register}/concepts/{id}.ttl
/data/{register}/concepts/{id}.jsonld
/data/{register}/concepts/{id}.json
/data/{register}/concepts/{id}.yaml
/data/{register}/concepts/{id}.tbx.xml
```

Aggregate downloads:

```
/data/{register}/index.json
/data/{register}/manifest.json
/data/{register}/edges.json
/data/{register}/domain-nodes.json
```

These paths are stable within a major version. Format additions
(e.g., a future `.nt` dump) are additive — never replace an existing
extension with another.

## Redirects

When a concept slug is renamed, the build pipeline emits a
`public/_redirects` entry (GitHub Pages / Netlify format):

```
/dataset/{register}/concept/{old-slug}  /dataset/{register}/concept/{new-slug}  301
/data/{register}/concepts/{old-slug}.ttl  /data/{register}/concepts/{new-slug}.ttl  301
... (one rule per format)
```

The redirect table is generated by `scripts/generate-data.mjs`
reading a per-dataset `redirects.yaml` maintained by hand when
renames happen. The redirects file is **append-only** — old entries
stay forever so external links from years ago still resolve.

In the v0.8.x stream no renames are planned; the redirects file is
empty by default.

## Out of scope

The following are NOT covered by this stability promise:

- **Internal serializer versions** — query strings like `?v=2` on
  internal API calls may change without notice.
- **Namespace prefix choices** — `xl:` → `skosxl:` style renames are
  presentation-level. The underlying IRIs are stable; the prefixes
  used to abbreviate them in Turtle may change.
- **Internal blank-node identifiers** — blank node labels are
  ephemeral per-document; never cite them.
- **JSON-LD context key names** — the JSON-LD `@context` may grow
  new keys; consumers must tolerate unknown keys (forward-compat).
  See [data-consumers.md](data-consumers.md).

## Versioned resource URIs (optional)

For datasets where publishers want stable-in-time URIs, the
manifest field `versioned_urls: true` enables:

```
/data/{register}/concepts/{id}.{ext}              → latest
/data/{register}/v/{version}/concepts/{id}.{ext}  → frozen at version
```

The latest path is the canonical URI in RDF; versioned paths are
accessible but not advertised. No dataset currently enables this;
the mechanism is documented for future opt-in.

## Major version migration

If a future v1.0.0 ships with breaking URL changes:

1. A `glossarist migrate` CLI command reads v0.x data, emits v1.x data.
2. Migration scripts are versioned (`migrations/0001-rename-predicate.rb`).
3. concept-model publishes a "what changed" document per major version.
4. Old URLs continue to redirect for at least one major version.

No major version is planned for the current stream.

## Deprecation policy for predicates

When an RDF predicate is deprecated:

1. Mark `owl:deprecated "true"^^xsd:boolean` in the ontology.
2. Add `dcterms:date "YYYY-MM-DD"` to track when.
3. Continue emitting it for 2 minor releases.
4. Remove on the next major release.

SHACL tests emit a **build warning** (not an error) when a
deprecated predicate is still in use, so deprecations do not block
routine releases.

## Contact

For URL stability questions or to report a broken link, open an
issue against the deployment repository (see README § Known
deployments). Cross-deployment issues are escalated to
glossarist/concept-model.
